## 0. 一句话设计

**一个源质 = 一个主职；一条途径 = 一个子职；20 个等级 = 序列 9 到序列 0 的十次晋升。**

玩家在 1 级选择源质主职与所属途径（子职），此后每 2 级晋升一个序列，20 级抵达该途径的序列 0（真神/神话形态），主职本身则提供源质层面的通用权柄。

### 1.2 每个 Mod 的交付内容

- `SefirahCastle.pak` 等 9 个可直接安装的 pak 文件
- 每个 pak 内：主职 1 个 + 子职 2–5 个 + 20 级进度表 + 法术/被动/状态/装备数据 + 中英双语本地化
- 每个 Mod 独立可装载，互不依赖（除等级拓展外）

### 1.3 设计原则

1. **设定优先**：序列名、途径归属、权柄主题全部取自权威设定数据，不自创序列。
2. **机制保守**：只使用 BG3 已验证的机制（Boosts / Passive / Spell / Status / Selector / AllowImprovement），不引入引擎不支持的判定。
3. **数值对齐原版**：满环施法者对标法师/牧师，血量与法术位曲线见 §4.5。
4. **可验证**：每个 Mod 产出后必须通过 §8 的五项自检。
5. **可扩展**：22 条途径特性各自独立，不写死跨 Mod 引用，避免装 8 个时互相污染。

## 3. 技术架构

### 3.1 pak 内目录结构（每个 Mod 同构）

```
Mods/<Folder>/meta.lsx
Public/<Folder>/
  ClassDescriptions/ClassDescriptions.lsx
  Progressions/Progressions.lsx
  Progressions/ProgressionDescriptions.lsx
  Lists/SpellLists.lsx
  Lists/SkillLists.lsx
  Lists/PassiveLists.lsx
  ActionResourceDefinitions/ActionResourceDefinitions.lsx
  DefaultValues/Abilities.lsx
  CharacterCreationPresets/AbilityDistributionPresets.lsx
  Stats/Generated/Data/Passive.txt
  Stats/Generated/Data/Spell_Shout.txt
  Stats/Generated/Data/Spell_Target.txt
  Stats/Generated/Data/Spell_Projectile.txt
  Stats/Generated/Data/Status_BOOST.txt
  Stats/Generated/Equipment.txt
  GUI/Icons_<CODE>.lsx
  Assets/Textures/Icons/<Code>Icons.DDS
Public/Game/GUI/Assets/ClassIcons/<Class>.DDS
Public/Game/GUI/Assets/ClassIcons/hotbar/<Class>.DDS
Localization/Chinese/<Folder>.xml + .loca
Localization/English/<Folder>.xml + .loca
```

### 3.2 引用链（必须闭环）

```
meta.lsx(UUID)
  └─ ClassDescriptions: UUID → ProgressionTableUUID
       └─ Progressions: TableUUID → UUID(每级)
            ├─ SelectSkills → SkillLists.UUID
            ├─ SelectSpells / AddSpells → SpellLists.UUID
            ├─ SelectPassives → PassiveLists.UUID
            └─ PassivesAdded → Passive.txt 的 entry 名
                 └─ SpellData → StatusData → DisplayName/Description handle
                      └─ Localization/*.loca
```

### 3.3 命名与 UUID 规范

| 对象 | 规则 | 示例 |
|---|---|---|
| Mod 文件夹 | 源质英文 PascalCase | `SefirahCastle` |
| 主职 Name | 同文件夹 | `SefirahCastle` |
| 子职 Name | 途径英文 | `Fool` / `Door` / `Error` |
| 资源名 | 语义英文，全局唯一 | `Spirituality` / `Divinity` / `Netherbreath` |
| 被动/法术/状态 | `<代号>_<语义>` | `SC_SpiritSurge`、`CS_Sunlight` |
| 本地化 handle | `h` + 确定性 UUID 去连字符 | `h4aa80458g9b46g...` |
| UUID | `uuid5(NAMESPACE, "<Folder>/<语义key>")`，全项目固定命名空间 | 见实现脚本 |

**强制约束**：不同 Mod 的同名对象必须带各自代号前缀，避免装多个 Mod 时 Stats entry 冲突。

### 3.4 本地化规范

- 每个 Mod 提供 `Chinese` 与 `English` 两套 `.xml` + `.loca`
- `.xml` 为可读源文件，`.loca` 为游戏实际读取格式（`LOCA` + version 42 + 条目数 + key 区 + 文本区，条目 70 字节）
- 所有 `DisplayName` / `Description` / 职业名 / 子职名 / 特性名 必须双语齐备
- 未翻译项在发布前清零（自检项 §8.4）

### 3.5 打包与自检工具链

| 工具 | 职责 |
|---|---|
| `lspk.py` | LSPK v18 读写：40 字节头、272 字节 FileEntry、LZ4 block、64 字节对齐、0xAD 填充 |
| `build_<code>.py` | 由设计数据生成全部 XML/TXT/loca |
| `pack_pak.py` | 将 build 目录打包为 `.pak` |
| 自检脚本 | 解包 round-trip + 引用完整性 + 本地化覆盖 |

## 6. 通用系统设计

### 6.1 实现标签定义

| 标签 | 含义 | 落点文件 |
|---|---|---|
| **B** | 等级加成（Boosts），每级累加 | `Progressions.lsx` 的 `Boosts` |
| **P** | 被动（Passive），常驻或条件触发 | `Stats/Generated/Data/Passive.txt` |
| **S** | 法术（SpellData），主动施放 | `Spell_Shout.txt` / `Spell_Target.txt` / `Spell_Projectile.txt` |
| **T** | 状态（StatusData），光环/持续效果 | `Status_BOOST.txt` |
| **A** | 属性提升，走 `AllowImprovement="true"` | `Progressions.lsx` |
| **L** | 法术列表挂载 | `Lists/SpellLists.lsx` |

### 6.2 被动模板

```
new entry "SC_SpiritSurge"
type "PassiveData"
data "Name" "SC_SpiritSurge"
data "DisplayName" "h...;1"
data "Description" "h...;1"
data "Icon" "PassiveFeature_Generic_...;"
data "Properties" "IsHidden"
data "StatsFunctorContext" "OnCreate;OnLongRest"
data "StatsFunctors" "ActionResource(SELF,Spirituality,1,0)"
```

规则：
- 有视觉表现的被动**不加** `IsHidden`；纯数值被动才加
- 条件类被动用 `Conditions` + `StatsFunctorContext`（参考暮剑士 `ArmoredMageLightDefence`）
- 所有状态/被动加入 `StatusGroups "SG_RemoveOnRespec"`，保证洗点后清理

### 6.3 状态模板（光环类）

```
new entry "SC_LORD_AUTHORITY"
type "StatusData"
data "StatusType" "BOOST"
data "StatusPropertyFlags" "ApplyToDead;IgnoreResting"
data "AuraRadius" "6"
data "AuraStatuses" "IF(Enemy()):ApplyStatus(SC_LORD_AUTHORITY_DEBUFF,100,-1)"
data "Boosts" "ArmorClass(2);RollBonus(Attack,2)"
data "StatusGroups" "SG_RemoveOnRespec"
```

规则：
- 敌方减益光环统一用 `AuraStatuses` + `IF(Enemy())`
- 友方增益光环统一用 `IF(Ally())`
- 持续回合数写在第 4 个参数（`ApplyStatus(X,100,N)`）

### 6.4 法术模板

```
new entry "SC_Divination"
type "SpellData"
data "SpellType" "Shout"
data "Level" "1"
data "SpellProperties" "ApplyStatus(SELF,SC_DIVINATION,100,3)"
data "TargetConditions" "Self()"
data "UseCosts" "BonusActionPoint:1;Spirituality:1"
data "Icon" "Spell_Eyebite_Panicked"
data "SpellStyleGroup" "Class"
```

规则：
- 主动增益 → `Shout`；指向性伤害/控制 → `Target`；投射物 → `Projectile`
- 消耗统一写 `ActionPoint/BonusActionPoint + <资源>`
- 控制类加 `SpellFlags "IsHarmful"`，增益类不加
- 图标优先复用原版已有图标名，自有图标走 §6.6

### 6.5 装备与初始武器

```
new equipment "EQP_CC_SefirahCastle"
add initialweaponset "Melee"
add equipmentgroup
add equipment entry "WPN_Staff"
```

每个主职配 1 套初始装备，主题对应：源堡法杖、混沌海锤、永暗之河巨剑、母巢短杖、失序之国长剑、灾祸之城匕首、暗影世界巨镰、知识荒野法杖、光之钥轻剑。

### 6.6 图标规范

- 主职图标：`Public/Game/GUI/Assets/ClassIcons/<Class>.DDS`（300×300）
- 快捷栏图标：`.../ClassIcons/hotbar/<Class>.DDS`
- 自定义技能图标：`GUI/Icons_<CODE>.lsx`（`TextureAtlasInfo` + `IconUVList`，10×10 网格，UV 步长 0.1）
- 第一阶段可全部复用原版图标名，仅主职图标用占位 DDS，不阻塞功能

### 6.7 法术池构成规则

每个主职 1 个 `SpellList`，按以下优先级取用**原版法术**，避免新增法术带来的兼容负担：

1. 主题匹配的原版法术（如太阳 → 灼热射线、光耀爆发）
2. 通用法术补齐（护盾、迷踪步、加速、反制法术）
3. 每环 3–5 个，1–6 环共约 20–30 个
4. 子职专属法术（序列 7/9/13 等的主动技能）单独列表，不混入主列表

| 依赖 | 作用 | 状态 |
|---|---|---|
| **等级上限拓展 Mod** | 使 13–20 级可选择、可升级 | ❗ 当前缺失，需补齐 |
| BG3 本体（GustavDev / GustavX） | 基础数据 | 已在 meta.lsx 声明 |

### 7.2 软依赖

| 依赖 | 作用 | 缺省表现 |
|---|---|---|
| 7–9 环法术拓展（AdvancedTTSpells / SpellsOfExandria） | 方案 B 法术位 | 缺省自动退回方案 A，不影响 1–20 级 |
| MCM 代码库（VolitionCabinet） | 可选设置菜单 | 无设置菜单，功能正常 |

### 7.3 兼容性设计

1. **资源名全局唯一**：9 个 Mod 各用独有资源名，避免互覆盖
2. **UUID 命名空间隔离**：每个 Mod 用独立命名空间派生 UUID，杜绝碰撞
3. **不修改原版文件**：只新增 `Public/<Folder>/...`，不动 `Public/Shared/...`
4. **多职业规则**：每个主职额外提供 `IsMulticlass=true` 的 1 级节点，保证兼职可用
5. **洗点安全**：全部状态/被动带 `SG_RemoveOnRespec`

## 8. 验收标准

每个 Mod 出厂前必须通过以下 5 项，全部通过才可交付：

| # | 检查项 | 判定 |
|---|---|---|
| 8.1 | XML/文本可解析 | 全部 `.lsx`/`.xml` 通过 `ElementTree.parse`，零报错 |
| 8.2 | 打包 round-trip | 解包后逐文件比对，`mismatch = 0` |
| 8.3 | 引用完整性 | 所有 handle / UUID / entry 名均有定义，缺失集为空 |
| 8.4 | 本地化覆盖 | 中文、英文条目数与 handle 总数一致，无空串 |
| 8.5 | 进度表完整性 | 主职 1–20 级齐全、子职 10 个序列节点齐全、4 个 ASI 节点存在 |

附加人工验收（进游戏）：
- 角色创建可见主职与全部子职，图标不缺失
- 1 级可选子职，3/5/7/9/11/13/15/17 级弹出序列特性
- 20 级可正常获得神话形态
- 短休/长休资源恢复正确

### 9.2 单个 Mod 的制作步骤

1. 按 §5 提取该源质的数据表 → 写入生成器数据结构
2. 生成 21–30 个文件（§3.1）
3. 执行 §8 的五项自检
4. 打包 `.pak`
5. 进游戏冒烟测试（创建角色 → 升到 20 级 → 验证特性）
